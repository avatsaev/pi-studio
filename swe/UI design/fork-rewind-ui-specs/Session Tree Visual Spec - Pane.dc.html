02Decision — the tree is a pane tab, not a dialoghandover Q1
CHOSEN · PANE TAB
The tree's whole job is orientation against the transcript. A pane tab can be split beside it, so the user reads "where am I" and "what is there" at once — a modal makes them alternate.
Panes already carry full window height. A 300-node tree needs it; a dialog caps at ~70vh and then scrolls inside a scroll.
It survives: the user can leave the tree open across turns, which is exactly how the "user only" filter gets used as a table of contents.
Zero new shell work — the tab strip, close, and split affordances exist.
REJECTED
Large modal. Engineering's default. Blocks the transcript at the exact moment the user is comparing against it, and a modal that people want to keep open is the wrong primitive.
Right side panel (Files/Changes rail). 232px cannot hold indentation plus a 200-char preview. Rejected on width alone.
Slide-over. Gets the height but not the side-by-side, and adds a third overlay layer for no gain.

Tab title: ⑂ Tree · <session name>, truncated with ellipsis at the tab's flex width. Tab icon ⑂ distinguishes it from ◍ chat and ⍜ file tabs.
One tab per session. Re-invoking the menu item focuses the existing tab and refetches, rather than opening a second.
Fetch on open and on focus-after-blur. No polling, no live updates. A tree fetched 30 seconds ago is acceptable; §10 covers what happens when it turns out to be stale.
Default placement: the tab opens in the pane group the chat is in. If the user splits, the tree keeps the transcript's right side. Split state is the user's, not ours to force.
