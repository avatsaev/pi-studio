08After a successful fork
Spec correction — do not ship this frame as drawn. Verified against bundled pi 0.84.2: fork sets targetLeafId = selectedEntry.parentId, so the branch ends at the entry before the selected message — the forked-from message is removed from the transcript and survives only as the returned text in the composer. Three things below are therefore incorrect: the “fork point — this message is kept” label, the AFTER frame still showing that bubble in the transcript (as drawn it would appear twice — transcript and composer), and the RULES line “The forked-from message stays in the transcript”. Everything from the forked message onward leaves the transcript. See swe/features/conversation-fork.md § Ground truth; the §12 copy deck is unaffected (it never contains this label).

RULES
The forked-from message stays in the transcript; everything after it goes.
Prefill happens only if the composer is empty. A draft is never overwritten and never prompted about — the fork still succeeds silently.
Caret lands at the end of the prefilled text; the composer scrolls into view as the new bottom.
No success toast. The truncated transcript is the confirmation.
09Other windows on the same conversation
Decision — open question 2. Silent convergence. No dialog, no toast, no divider. A "conversation was forked" marker would be the only transient annotation in the transcript and would read as content; the truncation is self-evident. The change is announced to assistive tech only (§11).
The observing window does not prefill its composer and does not steal focus. If its composer holds a draft, the draft survives untouched.
10Motion
Decision — open question 1. Brief transition, not an instant cut. Removed rows fade to 0 over 140 ms, then the block collapses its height over 120 ms; the composer prefill lands after the collapse. The motion is what tells the user which rows left.
