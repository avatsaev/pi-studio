# Task 003 — Upload acknowledgement: `fileTransferAck`

- **Sprint:** sprint-096-desktop-protocol-followups

- **Area:** packages/protocol, packages/server (files)
- **Priority:** P1
- **Estimated size:** S
- **Depends on:** task-002

## Goal
Let a client ask the daemon to confirm that an upload was written, or to say why it was not.

## Context / why
Today the daemon sends nothing after the last upload frame and never reports a write error. A client cannot tell a finished upload from a failed one without listing the directory.

## Scope references
- `swe/features/desktop-client-protocol-followups.md` § 2 (`fileTransferAck`, `file_upload_complete`, `file_upload_request.ack`), § Compatibility, § Error handling
- `packages/protocol/src/{messages.ts,client-capabilities.ts}` (`SERVER_FEATURES`)
- `packages/server/src/files/file-transfer.ts`
- `packages/server/src/daemon/{bootstrap.ts,dev-bootstrap.ts}` (feature advertisement)

## What to build
- Protocol: server feature flag `fileTransferAck`; `file_upload_request.ack` optional boolean; a schema for the push `file_upload_complete { type, transferId, stream, ok, bytesWritten, error? }`.
- Server: when the request carried `ack: true`, send `file_upload_complete` to the uploading session after the target file is closed (`ok: true`, final byte count) or after a failure (`ok: false`, an error string). Without `ack`, behaviour is exactly as today.
- Failures that must be reported: the target directory cannot be created, the file cannot be opened, a write fails, the client sends `Error`, the session closes mid-upload (no push; nothing to send to).
- Tests: success with byte count; zero-byte upload; write failure; client-sent `Error`; no push without `ack`.
