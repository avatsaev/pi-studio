## What was implemented
- **One engine for the app**
  - `TransferEngine` is in Tauri's managed state (`transfers/engine.rs`). It is built in `main.rs` after the secret store is chosen, and its `inspector()` fills `Services::transfers`.
  - The connector takes `bridge_plan()` from the owner thread and reads the password on the blocking pool.
  - It dials with `net::dial` (15 s limit, 16 MiB message limit) and the entry's address normalised as `transport_open` does.
  - A refused plan becomes a `ConnectError`. It is retried for `local_not_ready`, `local_stopped`, `timeout` and `busy`, and final for the rest (`not_bridged`, `no_current`, `unsupported`, and so on).
- **Commands**
  - `transfer_upload`, `transfer_save` and `transfer_cancel` are in `commands.rs`, `build.rs`, the capability and `generate_handler!`. That makes 20 commands, and the exact-list test now says so.
  - All three answer `engine_off` under `--transfers page`. The spec's § 2 table says `transfer_cancel` has no errors, but § 1 says all four commands answer `engine_off`; I followed § 1.
  - Answers are `{bytes}`, `{cancelled}` or `{code, message}`.
  - A bad `id` or `path` is checked before a handle is spent, so the same handle still works afterwards.
- **Local ends** (`transfers/files.rs`)
  - `FileSource` opens the file on the blocking pool and takes its size from metadata.
  - `rewind` seeks to 0 and re-reads the size.
  - Errors carry the system's reason and no path.
  - `SaveSink` wraps `ClaimedSave`. Writes run on the blocking pool, and a write the engine drops is waited for by `discard`.
- **Event:** `transfer_progress` with `{id, state, done, total}`.
- **Leaving**
  - `boot` cancels all transfers and closes the connection (1001).
  - So do the daemon switch, the window's destruction (`transfers::on_destroyed`) and exit (`transfers::on_run_event`).
  - The switch and exit close the engine and the proxied connections together, each waiting at most 5 s.
- **Waking**
  - A wake or network signal (`resume::send`) and a successful `transport_open` call `engine.wake()`.
  - It is spawned on the async runtime, because the resume ticker thread is not inside tokio.
- **Cancel before the start (extra requirement)**
  - A `transfer_cancel` for an id the engine does not have is remembered for 10 s, with at most 64 ids kept and ids over 64 bytes never kept. A start with that id then settles as `cancelled`, and its save is discarded.
  - The ordering closes the race: remember first, then ask the engine. The start checks right after the engine has taken the transfer.
  - This is recorded in `desktop/docs/architecture.md` (the `transfer_cancel` row).
- **`ui.inspect`:** the hook maps the engine's snapshot to the shell's view. The entry id is shown only while the connection is not closed.
- **Log:** one info line when a transfer starts and one when it ends or fails. Both carry id, kind, daemon path and local path (`{:?}`-escaped). The end line adds bytes and duration, and a failure line adds the code. No password or handle is logged.
- **Not in the brief**
  - I added a `leave` parameter to `shell::switch::switch_to` and updated its five tests. The brief said to cancel "before the reload", but at that point the registry already points at the new entry. A transfer waiting to reconnect could then dial the new entry's daemon and resume or restart there.
  - I added `ClaimedSave::destination()` in the shell, used only for the log line.
