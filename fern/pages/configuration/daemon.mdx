subtitle: Environment variables and config.json for the long-lived daemon process.

The daemon reads `$PI_STUDIO_HOME/config.json` and the environment variables below — set them
before `pi-studio daemon start`, or pass them to `docker compose` (see [Docker](/configuration/docker)).
All are optional.

| Variable | Default | Purpose |
|---|---|---|
| `PI_STUDIO_HOME` | `~/.pi-studio` | State + config + logs directory |
| `PI_STUDIO_LISTEN` | `127.0.0.1:6767` | Daemon listen address (`host:port`); falls back to `config.json` `daemon.listen`. For LAN access set `0.0.0.0:6767` and `PI_STUDIO_PASSWORD` (a non-loopback bind without a password is refused: the daemon logs the reason and exits 1) |
| `PI_STUDIO_PASSWORD` | _(unset)_ | Require this password for connections (bcrypt-checked) |
| `PI_STUDIO_HOSTNAMES` | `localhost,*.localhost` | Allowed `Host` header values (literal IPs always allowed) |
| `PI_STUDIO_DEV_ALLOWED_ORIGINS` | _(empty)_ | Developer switch: comma-separated browser `Origin`s (exact scheme+host+port) the direct WebSocket port accepts; overrides `config.json` `daemon.devAllowedOrigins`. Any other `Origin` gets `403 Origin not allowed`; requests without an `Origin` (CLI, desktop) are unaffected. Logs a `warn` at start when non-empty |
| `PI_STUDIO_SERVER_ID` | _(generated UUID)_ | Stable server identity |
| `PI_STUDIO_LOG_LEVEL` | `info` | pino log level |
| `PI_STUDIO_RELAY_ENABLED` | `false` | Opt in to dialing out to a relay — see [E2EE relay](/configuration/relay) |
| `PI_STUDIO_RELAY_ENDPOINT` | _(unset)_ | Relay `host:port` to dial |
| `PI_STUDIO_RELAY_USE_TLS` | `false` | Use `wss://` to reach the relay |
| `PI_STUDIO_UPDATE_AUTOCHECK` | `true` | Check for a newer daemon (npm, or the `daemon-updates` release for the single binary) at start, every 6 h, and when a client connects whose last check is over 10 minutes old (`config.json` `daemon.update.autoCheck`); `false` or `0` turns the automatic check off, "Check now" still works. The environment wins over `config.json` |
| `PI_STUDIO_INSTALL_KIND` | _(detected)_ | `npm-global`, `docker`, `source`, `binary` or `unknown`; wins over detection and decides whether the daemon can update itself. The Docker image sets `docker`; the single binary is detected as `binary` |
| `PI_STUDIO_DAEMON_UPDATE_URL` | the `daemon-updates` release's `latest.json` | Where a single-binary daemon reads the newest release; for tests and private release channels |

Example — run on a different port with a password and an isolated home:

```bash
PI_STUDIO_HOME=/tmp/pi-studio-dev \
PI_STUDIO_LISTEN=127.0.0.1:6790 \
PI_STUDIO_PASSWORD=hunter2 \
pi-studio daemon start
```

## Passwords and pairing keys

A password can also be set on an already-running daemon:

```bash
pi-studio daemon set-password hunter2
```

This bcrypt-hashes the password into `config.json` and enforces it on the daemon's next start.

To revoke every pairing link/QR ever issued (for example, one that leaked), mint a fresh keypair:

```bash
pi-studio daemon rotate-key
```

The daemon mints a new keypair, restarts, and prints a fresh QR — all clients must re-pair, but
your password and relay settings are untouched.

## Updating the daemon

A daemon installed with `npm i -g @av-pi-studio/cli`, or the single `pi-studio` binary (the desktop app's own
daemon, or one downloaded from a `daemon-v<version>` release), can be updated from any client that is
connected to it: the web UI shows a "Daemon X" pill when a newer version is available (on npm for the package;
in the `daemon-updates` release of the Pi-Studio repository for the binary). Settings → Daemon has "Check now"
and the automatic-check switch. The desktop app's Daemons screen also has an Update button for a local or SSH
daemon that is stopped or older than the app expects; it installs the binary the app was built with and then
starts the daemon.

For the npm package, the update installs the new CLI and daemon with `npm install -g`, updates the installed
extensions, restarts the daemon on the same address and waits for it to answer with the new version
(`GET /api/health` carries `version`). If the new version does not start, the previous one is installed again
(from npm's cache) and started, and the client says so. For the binary, the update downloads the archive,
checks its SHA-256, unpacks it into `$PI_STUDIO_HOME/bin/versions/<version>`, updates the extensions, points
`$PI_STUDIO_HOME/bin/current` at it and restarts the daemon; if the new version does not start, `current` goes
back to the old one, and that version is not offered again until a newer one appears (Check now still
offers it). Clients reconnect by themselves; agents and terminals on the old daemon end, and the update dialog
counts them first. The helper's log is `$PI_STUDIO_HOME/logs/update-restart.log`.

The daemon cannot update itself in Docker (replace the image), from a source checkout, when npm's global
folder is not writable or `npm` is not on the `PATH` (it shows the command to run by hand), for a binary run
from outside `$PI_STUDIO_HOME/bin/versions/` (it names the releases page), or on Windows. From a terminal,
`pi-studio update` updates the CLI or the binary and restarts a running local daemon.

`PI_STUDIO_DAEMON_UPDATE_URL` replaces the address of the binary's release manifest; it is meant for tests and
private release channels.

## Remote status and logs

A connected, authenticated client (direct or through the relay) can read the daemon's status and
stream its logs: when `server_info.features.daemonObservability` is `true`, the `daemon_status_*`
and `daemon_logs_*` messages are available. Log streaming mirrors the logger at its configured
`PI_STUDIO_LOG_LEVEL` (a client can only narrow it) and is rate-limited to 200 lines per second
per client; the log file and stdout are unchanged. Sensitive-looking fields and bearer tokens are
redacted before a line is streamed, but redaction is best-effort, not a guarantee. No new
environment variable is involved.

## The `pi` provider

The `pi` CLI is bundled inside `@earendil-works/pi-coding-agent` — the daemon launches
`node <pkg>/dist/cli.js --mode rpc`, so no global `pi` install is required. You only need pi
*authenticated*; see [CLI reference: Daemon & Auth](/cli-reference/daemon-and-auth#auth) for
`pi-studio auth login`, or set `ANTHROPIC_API_KEY` (etc.) directly in the daemon's environment.

To use a different `pi` than the bundled one, point the daemon at an absolute path in
`$PI_STUDIO_HOME/config.json`:

```json
{ "agents": { "providers": { "pi": { "command": ["/abs/path/to/pi", "--mode", "rpc"] } } } }
```

A missing or unresolvable `pi` surfaces as a clean `rpc_error` ("Pi provider unavailable…")
instead of crashing the daemon. A literal `~` in a `cwd` field is expanded to your home
directory. For a dependency-free smoke test, use the `mock` provider instead of `pi`.
