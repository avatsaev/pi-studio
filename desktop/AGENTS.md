# AGENTS.md

Pi Studio Desktop is the native client for a Pi-Studio daemon: a Tauri window whose webview runs
the workbench (`@av-pi-studio/workbench`, the same UI as the browser client), and a Rust side for
what a browser does badly: sockets, files on disk, secrets and OS integration. Read
`docs/architecture.md` next.

**Where it stands.** Milestone 1 (the native host and the daemon registry) is built and checked
live on Linux; on macOS and Windows only the automated checks have run (GitHub runners, 2026-11-20:
`.github/workflows/desktop-platform-checks.yml`; `docs/platform-checks.md` lists them and what a person
still runs). The window draws the workbench with a desktop host: at start the page calls `boot` (the
stored workbench keys, the registry view, the preview kind), and every storage write goes back
through `storage_set` to the Rust engine, which writes the files in the configuration directory.
Confirm and alert dialogs, external links and save-to-disk are native, through Rust commands, and
the HTML preview is served from an origin of its own. The engine holds the daemon registry
(`daemons.json`, version 3, mode 0600, no secret in it; local, direct, relay and SSH entries; the secrets
are in a store the engine is given: the keychain when it answers, else `secrets.json`; `--secret-store`
forces one) and the settings; a supervisor runs
the installed `pi-studio` CLI to start, stop and restart this machine's daemon. The window opens on
the entry used last; a native Daemons menu and the workbench's switcher and Daemons screen switch,
add, edit and remove entries, each with its own stored layout. All of it sits behind a command
registry that the page, the CLI and the control socket dispatch into. The socket to every entry's daemon is Rust's
(milestone 2 for `local` and `direct`, milestone 4 for `relay` and `ssh`): the host's `connection.createTransport`
(`src/host/connection.ts`) returns, for a current entry of any kind, the SDK's WebSocket transport pointed at the single-use
loopback address that the page's command `transport_open` answers after Rust opened the daemon's socket (a dial, the relay's
sealed channel, or a channel of an SSH session: `src/host/proxied-transport.ts`, `src-tauri/src/transport.rs`); with no
current entry the browser host's own transport is used. A
refused `transport_open` is reported to the SDK as a close (1006) after the rejection, as the SDK's own
transport does for a failed connect: the daemon client leaves "connecting" only on a close, so without
it the connection bar never shows the message or Retry. Checked live on Linux (2026-11-22,
`docs/development.md` § The transport proxy in the real webview). The runner workflow also checks it
on macOS (the local daemon's transport, the wake signal, the login keychain) and on Windows (a stand-in
daemon, the wake signal, the Credential Manager); those checks are written and tested on Linux and wait for their first run.
Milestone 3 (the transfer engine) is built in Rust and wired to the workbench: for every entry (relay and SSH since
milestone 4) the Upload button opens the native open dialog (`upload_pick`) and an upload or a save runs on a second
connection of Rust's own (`transfer_upload`, `transfer_save`, `transfer_cancel`, the `transfer_progress` event;
`--transfers page` turns it off, a dropped file and a `Blob` keep the page's path). Checked live
on Linux against a production daemon (2026-11-22, sprint-122/task-007; `docs/development.md` § The transfer
engine in the real webview): the native open and save dialogs driven with `xdotool`, three at once and the
rest queued, a connection cut or a daemon stopped mid-transfer (a save resumes, an upload starts again), a
refused password, a changed daemon file, the switch and window-close questions, the page's path, and a
command left pending for 10 minutes. The 5 GiB check ran on Linux over loopback on 2026-11-22 (sprint-123/task-001;
`docs/platform-checks.md` § Milestone 3, recipe in `docs/development.md` § The 5 GiB check): both directions
hash-equal, `peakHeld` 32 KiB (upload) and 1 MiB (save), 3 to 7 times the rate of `--transfers page` (about 490 and
1000 MiB/s against 160), the terminal's echo unchanged, and one mark missed: the daemon grew 91 to 94 MiB on the
first upload into a fresh daemon (64 MiB allowed). The page's path held a 5 GiB upload in the web process (up to
8 GiB resident). macOS and Windows are not checked (owner's decision, 2026-11-22); a sleep during a transfer was not run.
Known gaps: a layout change in the last ~250 ms before the window closes is lost; a file dragged from the OS
file manager was not tried (the page's drop was dispatched as an event); a `kill -9`ed daemon leaves its
`.pistudio-upload-<hex>.part` until it starts again, and the explorer lists it meanwhile. The app's `minDaemonVersion`
(`cli_answers::MIN_CLI_VERSION`, also the oldest CLI the supervisor accepts) is 0.0.127: the release
that carries the daemon's temporary-file and pacing changes. `main` published 0.0.126 from older code
while the branch was open, so the number is the one the branch's merge publishes.
Milestone 4 (the relay in Rust and SSH entries) is built: a relay entry's socket is Rust's (`relay`, protocol 2; the
pairing link never reaches the page), and an SSH entry (`ssh`: `~/.ssh/config`, jump hosts, agent, key files, a stored
password, host keys in the app's own `known_hosts`) reaches a daemon that listens on the host's loopback only, with a Start
button that runs `pi-studio daemon start` over the same connection. Every kind goes through the same proxy and the
same transfer engine. macOS and Windows are not checked (owner's decision, 2026-11-22).

This directory is the Cargo workspace root, inside the pi-studio monorepo: every path and command
in this file is relative to `desktop/`. The frontend (`apps/pistudiodesktop`) is an npm workspace
of the repository root, so its dependencies are in the root `package-lock.json`: install them with
`npm ci` at the repository root, never here.

If the `av-rust-desktop-*` agent skills are installed, use them: `av-rust-desktop-develop` for
everyday changes, `av-rust-desktop-architecture` for the rules in depth.

    crates/transfer         L8  the transfer engine (`limits.rs` holds every limit and `Limits` lets a test shorten one, `error.rs` the one `Error` enum (`Dial`, `UnsupportedDaemon`, `Protocol`, `Timeout`, `Rpc`, `Closed(Ended)`, `Internal`; `Ended` is `Local`, `Remote(code)`, `Silent` or `Socket`), `wire`: the daemon's frames with no socket or state; `wire::outbound` builds the text frames (`hello`, the upload, download and cancel requests, `ping`, `pong`), `wire::inbound` reads `Inbound::parse(text)` no further than needed (`ServerInfo`, `Reply` with typed readers for the three answers, `RpcError`, `UploadComplete`, ping, pong, `Other` by its type), `wire::binary` builds an upload's `Begin`/`Chunk`/`End`/`Error`, `decode`s a download's and says with `is_file_transfer` whether an opcode is `0x10`–`0x13`; every number from the daemon is 0 to 2^53 − 1 kept as `u64`, a broken frame is `Error::Protocol` and never repeats the daemon's words; its tests read the fixtures in `packages/protocol/fixtures/external-clients/` and run a seeded hostile loop); `connection`: the bulk connection. `Connection::open(DaemonSocket, &Hello, Limits)` takes the socket the connector gave (a WebSocket over TCP or TLS, an SSH channel or a relay's sealed channel: the crate does not know which, and there is no `Transport` trait; a test builds one over a pipe), sends `hello`, waits for `server_info` and requires its three flags (`Error::UnsupportedDaemon` otherwise), then starts a reader task and a writer task. `request(build)` sends a `session` frame with a fresh `requestId` and returns its answer, its `rpc_error` as `Error::Rpc`, or `Error::Timeout` after the answer time for that request alone. `send_text` and `send_binary` return when the frame is on the socket. `expect_upload(transferId)` gives an `UploadWait` for the one `file_upload_complete` with that id. `download()` takes a stream id from 0 to 255 and gives a `Download` whose `next()` returns `Delivery` values (a `Frame` and its share of the hold): the reader takes no frame off the socket while the consumer holds more than `download_hold_bytes` unreleased, so memory stays flat and the other transfers wait behind a slow one. The reader sends one `ping` after `ping_after` with no frame of any kind and drops the connection (`Ended::Silent`) after `dropped_after`; time spent blocked on a consumer does not count. A message above 16 MiB, text that is not UTF-8 or a frame `wire` cannot read ends it with `Error::Protocol` (close 1002); text and binary frames nobody awaits are ignored. However it ends, every waiter is told once with the reason (`Error::Closed(Ended)` or the protocol error; a download first gets what was queued), `ended()` waits for it, `close(Close::Normal | Close::GoingAway)` waits `close_wait` for the daemon's close frame, and dropping the connection ends it as `Local` with a 1001 close. Closing an idle connection, reconnecting and the queue are the engine's, not the connection's. `download`: one save over an open connection, `save(&Connection, Request { path, resume }, &mut impl Sink, progress, cancel, &Limits)`. A `Sink` is `written`, `write`, `finish` and `discard` (the app implements it over a save; `MemorySink` under `testing`). A stream id from the connection's pool is registered before `file_download_request` is sent, with `offset` and `ifUnchanged { size, mtimeMs }` only on a resume (`Version` is the first answer's `totalBytes` and `mtimeMs`; the offset is the sink's `written`) and never a `length`. The answer must name that stream and offset and a range that ends at the file's end, a resume must get the file it guarded, and `Begin` must repeat the answer, or it is `protocol`. Each `Chunk` is written before the next frame is taken, so at most the download hold is held. It is done when `End` came and exactly the announced bytes were written; then the sink is finished (more bytes, a `Chunk` before `Begin` or an early `End` is `protocol`). It returns `Saved { version, bytes }` or a `SaveError` with a `code()`: `Changed`, `DaemonRefused { reason }`, `Disk { reason }`, `Cancelled`, `Protocol` and `Internal` each discard the sink, and `ConnectionLost { reason, version }` (the connection ended, or the request got no answer) leaves it open to resume into and carries the file's `Version`. `cancel` is a future, as for `upload` (a ready one sends nothing, one during a write drops the write, one during `finish` waits for it). Any stop before the daemon's terminal frame sends `file_download_cancel_request` and keeps the stream id reserved until the daemon's last frame (an `Error` may be the first and only one), a refusal, a cancel answered `not_found` before the request was accepted, or the connection's end; after `answer_wait` a task of its own keeps the reservation, taking and dropping frames. `progress` gets `Progress { done, total }` when the daemon accepts and after each write. `upload`: `upload(&Connection, Target { path, transfer_id }, &mut impl UploadSource, progress, cancel, &Limits)` runs one upload over an open connection (the request with `ack`, `Begin`, `Chunk`s of at most 32 KiB each awaited before the next read, `End`, then the wait for `file_upload_complete`; done when it says `ok` with `bytesWritten` equal to the bytes sent) or returns an `UploadError` with a `code()` (`Cancelled`, `DaemonRefused`, `SourceUnreadable`, `SourceChanged`, `SizeMismatch`, `Protocol`, `ConnectionLost`, `Internal`); a stop after the daemon's answer sends `Error` (`client_aborted` on a cancel, `client_error` otherwise) so that it keeps nothing, and a cancel while the request is unanswered waits for the answer (at most `close_wait`) to free the stream the daemon chose. An `UploadSource` is `size`, `read` and `rewind` (back to the first byte, for a restart). `engine`: `Engine<C: Connector>::new(connector, Config { client_id, app_version, limits }, events)` is the object an app drives. `upload(id, path, source)` and `save(id, path, sink)` resolve when the transfer has settled, with the bytes or a `Failure { code, message }` (`id` is 1 to 64 characters of `A-Za-z0-9-`, else `invalid_request`; one that is running or waiting is `duplicate_id`; a path is 1 to 4096 bytes; a refused save's sink is discarded); `cancel(id)` settles it as `cancelled`; `cancel_all_and_close(Close)` cancels every transfer, waits for each to settle and closes the connection (1000 or 1001), and the engine can be used again; `snapshot()` is `transfers` of the control socket less `mode` and `entryId` (the connection's state and how often it opened, the active transfers with kind, state, bytes done and total and restarts, how many are queued, totals of done, failed and cancelled, `peak_held`, the last error with its time; no path). `Connector::connect` gives an open `DaemonSocket`, or a `ConnectError { code, message, retry }`. At most three transfers are active and the rest wait first in first out, with no limit; the connection is dialled when the first becomes active (until it is open the active ones are `waiting`) and is closed with 1000 thirty seconds after nothing is active or queued, a transfer that starts before that keeping it. The events callback gets `Event { id, state: queued | running | waiting, done, total }` at every change of state and at most once per `Limits::progress_interval` (100 ms) per transfer while bytes move, and none at settlement; it runs on the task that changed the state and must not call the engine. Recovery (D5, D12): a connection that cannot open or that drops makes the active transfers `waiting` (one event each) and the engine dials again at once after a drop, then after 1 s doubling to 30 s, with no limit on attempts and the delay back to 1 s on an open; `Engine::wake()` ends a wait at once (the app calls it on a wake, a network change, and when the page's own connection opened) and the delays go on growing if the dial fails again; with nothing active or queued the engine stops dialling. A `Connector` error is final when `retry` is false or its code is one of `FINAL_CODES` (`unauthorized`, `host_not_allowed`, `tls`, `invalid_address`, `secret_missing`, `secret_unavailable`, `no_current`, `unsupported`, `unsupported_daemon`, `protocol`; the relay's `wrong_key`, `daemon_outdated`, `protocol_error`, `invalid_link`; an SSH entry's `auth_failed`, `host_key_unknown`, `host_key_changed`, `passphrase_needed`, `key_unreadable`, `forwarding_refused`, `ssh_config`); an error of the `hello` exchange is final by that list or when it is `internal`; everything else, `handshake` included, is retried. A final error fails every active and queued transfer with its code; a transfer still running on a connection that ended settles when its attempt returns. After a reopen a save resumes (`offset` = the sink's `written`, `ifUnchanged` from its first answer; `changed` fails it and discards the sink) and an upload starts again from byte 0 with a new `transferId` after `UploadSource::rewind`, its progress back to 0; each counts a restart in the snapshot when it runs again. A cancel while waiting settles at once, a save is discarded then. `ConnectionState::Waiting` is the control socket's `waiting`. A panic in a transfer is `internal`. `held` is the gauge behind `peak_held`: an upload's read buffer from the moment it runs, and the frames of a download that the daemon sent and the sink has not written (`Connection::open_counting`); neither grows with a file. All the queue's state is under one lock in `engine/queue.rs`; the type-erased uploads and saves are `engine/work.rs`; the engine's tests run on the stand-in, moving a frozen clock by hand for the idle close, the events' rate and a save in flight, and the stand-in records the close codes it reads (`client_closes()`) and every download request (`download_requests()`); the recovery tests drive a scripted connector over the stand-in (refusals, a 502, a password dropped at a reopen) on a frozen clock; the hardening tests (`engine/tests/`, helpers in `rigs.rs`) are `stages.rs` (a table of an upload and a save each dropped or cancelled at six stages, from before the request to the wait to reconnect, each row saying how the transfer ends, that no half-written file is kept, that the sink is finished or discarded once and that `streams_in_use()` is 0), `hostile.rs` (every stand-in fault and a raw hostile WebSocket server: the connection ends as `protocol` or the transfer with its code, nothing held beyond the limits, no panic in the library, which a test-only panic hook counts), `soak.rs` (seeded: 60 rounds of three transfers with random faults and cancels, every one settles and what completed is byte-exact; short real time limits, about a second), `markers.rs` (a password, a local path, a handle-like string and the daemon's path planted in the connector, the daemon, a source and a sink, and searched for in every failure, event and snapshot) and `counters.rs` (5 GiB through a source and a sink that hold no byte, a resume offset past 4 GiB). `tokio`, `tokio-tungstenite` and `futures-util` are normal native dependencies; `testing` (the `testing` feature and this crate's own tests only; an app lists the feature in its `[dev-dependencies]`, so a release build has none of it): `StandInDaemon::start()` / `start_with(Config)` is a WebSocket daemon in the test's process on `127.0.0.1` (OS-assigned port, `url()`) that answers the upgrade (an optional password, else 401), `hello` with a `status` whose feature flags are `Config::features`, `ping`, uploads into memory (kept at their path only when `End` arrived; ## Golden rules

1. The UI is the workbench. `apps/pistudiodesktop/src` only mounts `@av-pi-studio/workbench` and
   gives it a host (`WorkbenchHost`). View state (sessions, timelines, panes, settings) lives in the
   workbench, in TypeScript, shared with the browser client: change the UI in `packages/workbench`,
   not here. This package makes no network call and stores nothing of its own (oxlint enforces
   it); what the platform must do is a member of the host.
2. Never crash. Non-test Rust code has no unwrap, expect or panic, and no unsafe. Return errors.
   Input is hostile: check bounds, cap sizes, bound recursion. A crash fix ships with a test that
   panicked before it.
3. Everything the Rust side does for a user is a command, in `crates/engine/src/*_cmds.rs`, with
   id, label, menu, shortcut, params doc, `enabled`, `run` and tests. The CLI and the control
   channel dispatch ids.
4. A crate depends only on lower layers. Nothing below the app binary uses tauri, wry or tao.
5. The workbench owns what the window shows. Colours, sizes and themes come from the design system
   (`@av-pi-studio/ui-library`); this package adds no tokens. Look at a rendered image
   (`npm run snapshot`) before calling a UI change done.
6. The webview gets the least it needs: it may call only the commands the build script's app
   manifest lists and the capability grants (`docs/architecture.md` § The webview boundary); no
   plug-in permission and no `core:` permission except listening to events (Tauri cannot scope it
   to names), no remote content in the main window, navigation only within the app origin, and a
   Content-Security-Policy that lists exactly the sources the workbench uses (`app.security.csp`
   in `tauri.conf.json`). Add a source or a command only with the feature that needs it;
   `npm run snapshot` fails when the page breaks the policy.
7. Never break wasm. File-system code is `cfg(not(target_arch = "wasm32"))` (the engine reads and
   writes the app's files through the `store` crate, which is empty on wasm32) or behind
   `Services`.
8. Tests are the gate. Every change comes with tests.
9. Permissive licences only, for crates and npm packages alike. Check a dependency's licence
   before adding it; record every bundled asset in `ATTRIBUTION.md`. Known exception, not yet
   decided: the workbench and `@av-pi-studio/ui-library` are AGPL-3.0 and are bundled into the app.
10. Secrets (a direct entry's password, a relay entry's pairing link, an SSH entry's password, key passphrase and
    daemon password) live only in the secret store (`crates/secrets`), never in `daemons.json` (version 3:
    `hasPassword`, `hasSshPassword`, `hasPassphrase`); the CLI's `pairingUrl` is discarded, also from the output of an
    SSH entry's Start. They are never logged, never in a control answer, in `boot` or in `ui.inspect`, and no command
    returns one, without exception. A secret never reaches the page: `daemon_resolve_current` answers `{url, connect:
    true}` with an address only (the entry's own; the relay's host for a relay entry; `ws://127.0.0.1:<daemonPort>` for
    an SSH entry), and `transport_open` reads the secrets itself, in Rust, for its dial and answers none
    (`Dial::Connect` has no password field; `tests/secret_guard.rs` fails if an answer gets one back, a pairing link
    included; the page's `connect-src` allows `ws://127.0.0.1:*` only). The log holds codes and fixed texts: never a
    link, a relay host, an SSH host or user, a key path, a fingerprint or the output of a remote command. A store call
    may block: the session never makes one on the owner thread (it plans a dial, `DialPlan`, and the
    caller reads the store; `daemon.add/update/remove` are a `SecretJob` whose store steps run on
    worker threads, `deferred.rs`), except at launch, where a version 1 file's secrets are moved.
    Which store a launch uses is chosen once, by `shell/src/secret_choice.rs` (shared by the app and
    its CLI): `--secret-store keychain|file`, else the keychain when a check (open, read a missing
    item, write and delete a throwaway one; 2 s in all, on its own thread) passes, else `secrets.json`
    with a notice; the app never opens a real configuration directory before that. Every automated
    or live run passes `--secret-store file`, so that none writes to a developer's keychain; the two
    exceptions are the runner workflow's keychain checks (`macos-keychain.mjs`, `windows-bridge.mjs`
    in `apps/pistudiodesktop/scripts/platform-checks`: `--secret-store keychain`, a scratch
    `--config-dir`, on GitHub's throwaway machines, deleting what they wrote; a unit test pins that no
    other script names the option). The kind
    is `secretStore` in the registry view and `connection.secretStore` in `ui.inspect`; nothing else
    of the store is shown. A `*.corrupt-*` copy of the file keeps its mode and may hold old secrets.

## Conventions

- Command ids (`<area>.<verb>`, camelCase) and control methods are public API. Never rename one
  after a release.
- An error says what was wrong and, where possible, what would be right.
- A command that cannot run now returns the reason: it is the menu item's tooltip and the message
  an agent reads.
- A check that looks removable carries a comment saying what it prevents.
- Machine names are lowercase (`pistudiodesktop`); everything a user reads says `Pi Studio`.
