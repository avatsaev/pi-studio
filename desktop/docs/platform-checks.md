# Platform checks (macOS and Windows)

The app was built and tested on Linux. On macOS (WKWebView) and Windows (WebView2) only the
automated checks of the last section have run, on GitHub's runners (2026-11-20, pull request #59):
the items they cover are marked there. Everything else on this page is for a person with one of
those machines, in under an hour, and the table at the end is where the results go. Each item has
steps and the result to expect.

## Get the app

1. On GitHub, run the **Desktop release** workflow on the branch by hand (Actions → Desktop release → Run workflow). A manual run builds the installers as workflow artifacts and publishes nothing.
2. Download the artifact for the machine (a `.dmg` for macOS, an `.msi` or the NSIS `.exe` for Windows).
3. The installers are not signed. **macOS:** open the app once, then allow it in System Settings → Privacy & Security ("Open Anyway"). **Windows:** SmartScreen says "Windows protected your PC": More info → Run anyway.
4. For every item below, start the app with a scratch configuration directory so it does not touch your own: `--config-dir <dir>` (macOS: `open -a "Pi Studio" --args --config-dir /tmp/pi-check`; Windows: `"Pi Studio.exe" --config-dir C:\pi-check`). A daemon to connect to: on the same machine, `npm i -g @av-pi-studio/cli` then `pi-studio daemon start` (macOS), or a daemon on another machine reached by address (Windows has no local daemon).

Items marked **automated** are also run by the workflow `desktop-platform-checks.yml` (see the last section); a person need not repeat them.

Notes on the numbers:

- **How they were measured.** Rates: from the file system, the first non-empty `.pistudio-*.part` to the final file at full size with no part left, polled every 50 ms (the engine's own log says 10 230 / 10 505 / 10 467 ms for the uploads and 4 733 / 5 582 / 4 723 ms for the saves). Memory: `VmRSS` from `/proc` on the host (the container's processes are visible there), sampled every 250 ms by group (`pistudiodesktop`, `WebKitWebProces`, `WebKitNetworkPr`, the daemon's `node`), growth being the peak minus the value 2 s before the transfer; a spike under 250 ms can be missed. Echo: the page's clock, 1 ms steps, the *n*th key paired with the *n*th echoed `z`, a key about every 63 ms for the whole transfer. The page-path runs had the same typing and the same recorder, so the rate comparison is like for like.
- **The web process.** Typing alone, with no transfer, grew `WebKitWebProces` by 42.7 MiB in 64 s (the harness's WebDriver keys and xterm; the daemon grew 6 MiB), so what the web process grew during a 5 to 10 s transfer is mostly that. The mark is missed as written, and it is the daemon's, not the app's: the app's own growth is under 12 MiB.
- **The page's path** completed 5 GiB in both directions with an equal hash, at 157 to 162 MiB/s in both. ## The automated workflow

`.github/workflows/desktop-platform-checks.yml` builds a debug app on a Windows and a macOS runner and runs the checks a machine can run (`apps/pistudiodesktop/scripts/platform-checks.mjs`). Until the workflow file is on `main`, GitHub offers no manual run for it (`gh workflow run` answers 404 "not found on the default branch"): it runs on a pull request that changes the workflow file (`gh run watch` follows it). Once it is on `main`: Actions → Desktop platform checks → Run workflow, or `gh workflow run desktop-platform-checks.yml --ref <branch>`. It never runs on a push to `main` and publishes nothing. **Read the job summary first:** it holds the printed facts (the Windows preview probe, the macOS configuration directory, where `daemons.json` is, the first daemon start's duration, which shells found the CLI, and, since milestone 2's checks, the connection's counters, the wake count before and after the stop, and whether the runner's keychain can be used unattended, with the reason when it cannot). Screenshots and logs are the `platform-checks-<os>` artifacts. A keychain check that cannot run on a runner is a skipped row with its reason, never a failed job.
