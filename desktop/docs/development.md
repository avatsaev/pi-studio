# Development

## Prerequisites

- **Rust** stable, 1.95 or newer, with `rustup component add clippy rustfmt` and
  `rustup target add wasm32-unknown-unknown`.
- **Node.js** 22.12 or newer (an even, LTS line), with npm.
- **Linux**: a C compiler, pkg-config, and the development packages Tauri builds against.

  | Distribution | Command |
  |---|---|
  | Debian, Ubuntu | `sudo apt install build-essential pkg-config libwebkit2gtk-4.1-dev librsvg2-dev libxdo-dev` |
  | Fedora, RHEL | `sudo dnf install gcc pkgconf-pkg-config webkit2gtk4.1-devel librsvg2-devel libxdo-devel` |
  | Arch | `sudo pacman -S gcc pkgconf webkit2gtk-4.1 librsvg xdotool` |

- **Windows**: the MSVC toolchain with the "Desktop development with C++" workload, and the
  WebView2 runtime (part of Windows 11 and of current Windows 10).
- **macOS**: the Xcode command line tools.
- **Optional**: `cargo install cargo-nextest --locked` (the parallel test runner; without it the
  gate falls back to `cargo test`).

Then, once: `npm ci` at the repository root. The frontend is an npm workspace of the monorepo, so
there is one lock file and one install, both up there.

## Commands

| Command | What it does |
|---|---|
| `cargo run -p pistudiodesktop` | Run the desktop app with the built frontend. Add `--release` for anything performance-sensitive |
| `npm run app` (in `apps/pistudiodesktop`) | Run the desktop app on Vite's dev server: frontend changes reload at once |
| `cargo xtask web` | The frontend: type check, lint, tests and build (`npm ci` at the repository root first when needed) |
| `npm run check` / `npm run lint` / `npm test` (in `apps/pistudiodesktop`) | `tsc -b` (also builds the type declarations of the monorepo packages it imports) / oxlint (type-aware; warnings are errors) / the tests (vitest) |
| `cargo test -p <crate> --lib --tests` | One crate's tests, skipping examples and doctests |
| `cargo test -p <crate> --test <file>` | One integration-test file |
| `cargo nextest run --workspace` | Every Rust test, in parallel across test binaries |
| `cargo clippy -p <crate> --all-targets -- -D warnings` | Lint what you touched |
| `cargo fmt --all` | Format |
| `cargo xtask layers` | Print the dependency table and any violations |
| `cargo xtask wasm` | `cargo check` for wasm32 on the layered crates |
| `cargo xtask ci` | The whole gate. Run it before you call something done |
| `npm run bundle` (in `apps/pistudiodesktop`) | Build installers with the Tauri bundler |

The gate runs, in order: `fmt`, `web`, `clippy`, `layers`, `test`, `panic_hunt`, `doctest`, `wasm`.

The frontend is embedded into the desktop binary at compile time, from `apps/pistudiodesktop/dist`. Any cargo
command that compiles the app (`cargo run -p pistudiodesktop`, `cargo clippy --workspace`) needs that
directory: run `cargo xtask web` (or `npm run build`) first, and again after frontend changes.

## Releasing

Installers are built and released by `.github/workflows/desktop-release.yml` (at the repository root),
not on a developer's machine, and the release is automatic: every push to `main` that Desktop CI
gates (a change to `desktop/` or to a package the app builds from) and that passes Desktop CI is
released. A failed Desktop CI run releases nothing.

- **What is built:** the commit Desktop CI checked, on three runners: `.deb`, `.rpm` and `.AppImage`
  (x64), one universal `.dmg`, and `.msi` plus an NSIS `.exe` (x64). The job `bundle-release` also
  makes the app's **update files** (the AppImage, `.deb`, `.rpm`, `.msi` and NSIS `.exe` themselves,
  and `Pi Studio.app.tar.gz` from the universal `.app`), each with a `.sig` made by the updater key
  (the overlay `{"bundle":{"createUpdaterArtifacts":true}}` is passed by that job only; `tauri.conf.json`
  never asks for update files). The release is **published** at once with fixed notes (the unsigned-build
  warnings and the CLI the local daemon needs), holds the installers, the update files, their `.sig`s,
  `latest.json` (the manifest naming this version) and `self-check.json`, and creates the tag
  `desktop-v<version>` on that commit. If a bundle job fails, no release is created.
- **Offering the build:** the release does not reach installed apps yet. The job `update-check` runs per
  system (Linux: the AppImage, then the `.deb`; macOS: the `.dmg`; Windows: the NSIS setup; fail-fast
  off) and, for each, installs the build the offered manifest names now (P: `desktop-updates/latest.json`;
  none the first time, then only the self check runs), launches it at this release's `latest.json`
  (`--update-manifest`), has it update itself to the new build through the control socket, and then
  proves the new build can update itself through `self-check.json`
  (`scripts/platform-checks/update-check.mjs`; § Platform checks). When all of them passed, the job
  `promote` puts this release's `latest.json` into the release **`desktop-updates`** (created with
  `--latest=false` the first time: never the repository's latest release; its tag does not match
  `desktop-v*`), the manifest the app's endpoint names. A failed check leaves the installers
  published and not offered; the next release's check starts from the build offered before. The
  checks' summaries are in the run's job summary, their logs in the artifacts `update-check-<system>`.
- **The version:** the desktop client has its own version line; it does not follow the npm
  packages'. Each release is the patch after the highest `desktop-v*` tag, unless
  `[workspace.package] version` in `Cargo.toml` is higher, which is then used as is. For a minor or
  major release raise it there in a pull request (run `cargo xtask ci`, which refreshes
  `Cargo.lock`). The version is written into the runners' copy of `Cargo.toml` before the build;
  nothing is committed back to `main`, so `Cargo.toml` holds the lowest version the next release
  can have, not the last one released.
- **Not released twice:** a commit that already carries a `desktop-v*` tag (a re-run) builds and
  publishes nothing. Releases run one at a time; when several merges land during one, only the
  newest waits, and it holds all of them.
- **To try installers before a merge:** run the workflow by hand on the branch (Actions → Desktop
  release → Run workflow): it builds and attaches the installers to the run as artifacts, and
  publishes nothing. A pull request that changes the workflow file, its action
  (`.github/actions/desktop-build-tools`), `scripts/release/`, `scripts/platform-checks/` or the test
  overlay does more: `bundle` makes two **test builds** per system, built exactly like the release (every
  format, the same target) with a throwaway key pair generated in the job, the overlay
  `src-tauri/tauri.update-test.conf.json` and its public key (P = 0.0.1 and N = the version the release
  would have), and `update-check` runs the whole check against `scripts/release/serve-directory.mjs`
  on `127.0.0.1:8791`, with manifests made by the same script as the release's. `release` and `promote`
  are skipped and no job of such a run names the environment or the secret. The automatic trigger
  itself only runs from the file on `main`.
- **The release scripts** (`apps/pistudiodesktop/scripts/release/`; tests `node --test
  scripts/release/*-test.mjs`, also run by the job `version`): `next-version.mjs` (the version rule; reads
  `git tag -l`, counts only `desktop-v<M.m.p>`, so the tag `desktop-updates` and others are ignored),
  `set-version.sh`, `update-manifest.mjs` (`latest.json`, `self-check.json`), `self-check-signatures.mjs`
  (signs a copy of each update file for the version `<N's next patch>-selfcheck` and keeps the result as
  `<file>.selfcheck.sig`; the signer needs the key in the environment), `serve-directory.mjs` and
  `daemon-pin.mjs` (`--manifest <url> (--min <v> | --min-from cli_answers.rs) --out <file> [--wait-minutes 30]`:
  reads `daemon-updates/latest.json`, retries every 60 s while its version is below `MIN_CLI_VERSION`,
  fails with `no daemon binary ≥ <min> is published`, and writes `{version, assets}` for the four
  targets; a developer runs it without `--wait-minutes` to refresh the committed `desktop/daemon-pin.json`).
  In a release run the job `version` runs it, only when `desktop/daemon-pin.json` is committed, and
  `bundle-release` writes the result into its checkout before the build.

The installers are not signed with a real identity. macOS gets an ad-hoc signature, so a downloaded
app must be allowed in System Settings → Privacy & Security; Windows shows a SmartScreen warning.
Real signing needs an Apple Developer ID and a Windows code-signing certificate, held as repository
secrets.

### The updater key

The app updates itself (`swe/features/desktop-self-update.md`); every update file is signed with a
key of our own, not an Apple or Microsoft one. The private half is in two places: the secret
`TAURI_SIGNING_PRIVATE_KEY` of the GitHub environment `desktop-release` (deployments from `main`
only; the secret is the key file's text, no password), and one file on the maintainer's machine,
`~/.config/pi-studio-release/updater.key` (mode 0600, no password, outside the repository), which is
the only copy to back up. The public half is `plugins.updater.pubkey` in
`src-tauri/tauri.conf.json`. Only `bundle-release` (and its staging step, which signs for the self
check) read the secret; no job of a pull request's or a manual run names the environment or the
secret, and the key never reaches a script that launches the app (`update-check.mjs` drops every
environment variable whose name looks like a secret).

**To set it up** (once; it is in place): the environment `desktop-release` with the deployment
branch policy "selected branches": `main`; then
`gh secret set TAURI_SIGNING_PRIVATE_KEY --env desktop-release < ~/.config/pi-studio-release/updater.key`.

**Re-running a failed check.** A failed `update-check` job leaves the installers published and the
offered manifest unchanged, and fails the run. Read the job summary (which step, which state the app
was in) and the artifact `update-check-<system>` (the app's logs). If the cause was not the build (a
runner, the network), open the run and choose "Re-run failed jobs": the failed `update-check` jobs run
again against the same release and the same offered build, and `promote` runs when they pass. If the
build is bad, merge the fix: the next release is built, checked from the build offered before, and
promoted; nothing is withdrawn.

**The key is lost** (both copies): installed apps can never update again. Make a new pair
(`npx tauri signer generate -w <file>` in `apps/pistudiodesktop`, empty password), put its public key
into `tauri.conf.json`, set the secret to the new private key, and release; both users install that
build by hand once. Keep the new file where the old one was.

**The key leaked.** Anyone holding it can sign an update, but an app only fetches the one manifest of
`desktop-updates`, which only a person with write access to the repository can change. To move to a
new pair without stranding installed apps: (1) make the pair as above and put the new public key into
`tauri.conf.json` in a pull request; (2) merge it while the secret still holds the **old** key: that
release is signed with the old key, so installed apps accept it, and from then on they carry the new
public key; (3) its self check **fails by design** (the build trusts the new key, the self-check
signatures are the old key's), so `promote` does not run: check in the job summaries that the update
step of every `update-check` job passed, then promote by hand
(`gh release download desktop-v<N> --pattern latest.json && gh release upload desktop-updates latest.json --clobber`);
(4) only then replace the secret and the local file with the new private key. Later releases are signed
with it and their checks pass again. (Not exercised: no key has been rotated.)

## Run the pieces

The CLI:

```sh
cargo run -q -p pistudiodesktop-cli -- commands --filter settings
cargo run -q -p pistudiodesktop-cli -- run --cmd settings.get
cargo run -q -p pistudiodesktop-cli -- run --config-dir ./cfg --secret-store file --cmd 'settings.set {"key":"autoStartLocalDaemon","value":false}' --cmd settings.get
```

`commands` lists the registry, one JSON object per line. `run` executes each `--cmd '<id> [json]'`
in order and prints `{"command": …, "result": …}` per step. With `--config-dir DIR` the session
reads and writes that configuration directory (`settings.json`, `daemon-state/<entry>.json`);
nothing is created until a command writes, so the third line leaves `./cfg/settings.json` behind.
Without it the session lives in memory and writes no file.

Results are JSON lines on standard output; diagnostics go to standard error. Exit status 1 is a
failed command, 2 a usage error.

The UI without the app. `npm run snapshot` serves the built frontend from a loopback port with the
app's Content-Security-Policy, draws it in a headless browser and saves a PNG. It exits 1 when the
page broke the policy or threw, so it is also the check for a change to the policy.

```sh
cd apps/pistudiodesktop
npm run snapshot:install        # once: downloads the headless browser
npm run build
npm run snapshot -- --out ui.png                       # the window before it connects
npm run snapshot -- --out ui.png --wait-for 'text=/^connected/i' \
  --query 'host=127.0.0.1:6767&connect=1'              # connected to a daemon on this machine
```

`--query` is the workbench's launch grammar (`host`, `password`, `cwd`, `connect=1`). `--steps FILE`
runs an ES module's default export, `async (page) => {}`, with the Playwright page before the
screenshot: open a workspace, send a message, open a file. A daemon to point it at:
`PI_STUDIO_LISTEN=127.0.0.1:6790 npm run dev:daemon` at the repository root (a mock agent, no
credentials).

This is how to check a UI change without opening a window. The browser is Playwright's Chromium
(or `--browser webkit`), not the platform webview the app runs in: trust it for layout, themes and
the policy, and check platform behaviour in the running app.

The running app, driven from outside: see `docs/control-protocol.md`.

## Configuration directory

The app keeps its files in `--config-dir <dir>` (or `PISTUDIODESKTOP_CONFIG_DIR`), else the
platform's app configuration directory — on Linux `~/.config/com.avatsaev.pi-studio`. It holds
`settings.json` (the app settings, with the workbench's app-wide keys under `workbench`),
`daemons.json` (the daemon registry, version 2: the entries, `hasPassword` for an entry that has a
secret in the secret store, and `lastUsedId`; mode 0600, no secret in it) and `daemon-state/<id>.json`
(the keys kept per daemon; `local` for this machine, the entry's id for the others). A file that
cannot be read is renamed to `<name>.corrupt-<time>`, the app starts with defaults and the page
shows the notice once. Point `--config-dir` at a scratch directory for tests and smoke runs.

**Where the secrets go.** `--secret-store keychain|file` (the app and its CLI): without it the app
takes the operating system's keychain when it answers within 2 s and accepts a throwaway item
(written and deleted at launch), else `secrets.json` in this directory (mode 0600), and the page says
so once (a notice) and on the Daemons screen. `file` never touches the keychain; `keychain` on a
machine without one fails the launch with a message that names the option. **Every automated or
live run passes `--secret-store file` with a scratch `--config-dir`**, so that nothing writes to a
developer's keychain: the commands in this document do, and so does
`apps/pistudiodesktop/scripts/platform-checks` (`SECRET_STORE_ARG`, checked by a unit test), with two
exceptions: the runner workflow's keychain checks (`macos-keychain.mjs` on macOS, the keychain part
of `windows-bridge.mjs` on Windows) launch with `KEYCHAIN_STORE_ARG` (`--secret-store=keychain`) and a
scratch `--config-dir`, on GitHub's throwaway machines, and delete the items they wrote; the same unit
test pins that no other script names it. The
keychain's items are named by the directory as it is given (a hash of the path; the default
directory is `default`), so the CLI sees the app's keychain secrets only when `--config-dir` names
the app's directory the same way, and not at all for the app's default directory: use
`--secret-store file` on both or neither.

### Pointing the app at a scratch CLI and home

The local daemon is run through the `pi-studio` CLI. Set `cliPath` (`settings.set`, or the Daemons
screen) to a script of your own to choose which CLI runs, for example one that execs the repository's
build: `exec node <repo>/packages/cli/dist/cli.js "$@"` (after `npm run build:cli`). The CLI inherits
the app's environment, so start the app with `PI_STUDIO_HOME=<scratch dir>` to keep the daemon's state
out of `~/.pi-studio`, and set `autoStartLocalDaemon` to `false` before the first launch, or the app
starts a daemon on launch. `daemon start` always listens on 6767 (`PI_STUDIO_LISTEN` does not apply),
so nothing else may hold that port. A fake CLI for failure cases is
`crates/shell/tests/fixtures/fake-pi-studio.sh` (modes in its header). Quitting the app leaves the
daemon it started running: stop it with `pi-studio daemon stop` under the same `PI_STUDIO_HOME`.

## Without a display

Running the window needs a display: `Xvfb :99 -screen 0 1280x800x24 &` and then
`DISPLAY=:99 cargo run -p pistudiodesktop -- --secret-store file` (the option keeps the run's secrets
out of your keychain; § Configuration directory). The snapshot tool and every test need none.

The `pi-desktop-xvfb` Docker image (Xvfb, WebKitGTK and WebKitWebDriver; no `nc`) runs the built
app with no display of your own. After `cargo build -p pistudiodesktop` (which needs
`apps/pistudiodesktop/dist`), mount the workspace read-only and talk to the control socket from
inside the container. Pick a scratch port other than 6767, which a daemon may use:

```sh
cat > /tmp/pi-smoke.sh <<'EOF'
cd /work
xvfb-run -a ./target/debug/pistudiodesktop --control 7979 --control-token-file /tmp/control.token --secret-store file >/tmp/app.log 2>&1 &
sleep 6
TOKEN=$(tr -d '\r\n' < /tmp/control.token)
exec 3<>/dev/tcp/127.0.0.1/7979
printf '%s\n' "{\"id\":\"auth\",\"method\":\"auth\",\"params\":{\"token\":\"$TOKEN\"}}" \
  '{"id":1,"method":"ui.inspect","params":{}}' >&3
for i in 1 2; do read -t 5 -u 3 line; echo "$line"; done
EOF
docker run --rm -v "$PWD:/work:ro" -v /tmp/pi-smoke.sh:/tmp/pi-smoke.sh:ro pi-desktop-xvfb bash /tmp/pi-smoke.sh
```

Expected: `{"id":"auth","ok":true,"result":{"authenticated":true}}`, then
`{"id":1,"ok":true,"result":{"daemons":{"currentId":"local","entries":[{"hasPassword":false,"id":"local","kind":"local","name":"This machine"}],"local":{"state":"cli_missing"},"settings":{"autoStartLocalDaemon":true,"cliPath":null}},"menus":[…],"settings":{…},"ui":{…}}}`
(the image has no `pi-studio` CLI, hence `cli_missing`).
This checks that the app starts and answers; for the window's pixels use `npm run snapshot`, and
for the webview itself WebKitWebDriver, as below.

To drive the real webview on Linux without a display, run the binary under WebKit's WebDriver
(`WebKitWebDriver`, Ubuntu package `webkitgtk-webdriver`) with `TAURI_WEBVIEW_AUTOMATION=true` in
its environment, and open a session with the capabilities `{"browserName": "wry",
"webkitgtk:browserOptions": {"binary": "<path to pistudiodesktop>", "args": ["--config-dir",
"<scratch dir>", "--secret-store=file"]}}`. Scripts, clicks and screenshots then go through the WebDriver protocol; from
an async script, `window.__TAURI_INTERNALS__.invoke('boot')` shows what the page booted with.

Three things the container does not give you by default:

- **A D-Bus session bus.** Without one the single-instance check never runs and a second launch
  opens a second window. Start one before WebKitWebDriver:
  `dbus-daemon --session --fork --print-address=3 3>/tmp/bus` and export
  `DBUS_SESSION_BUS_ADDRESS=$(cat /tmp/bus)`.
- **A window manager.** There is none, so focus cannot be observed, and closing the WebDriver
  session kills the app (no exit flush). To close it like a user, send `WM_DELETE_WINDOW` to the
  window `xwininfo -root -tree` lists as "Pi Studio" (an `XSendEvent` `ClientMessage`).
- **One app at a time.** The single-instance lock is per app identifier, not per configuration
  directory: two sessions at once collide.

### The keychain in the container

`crates/secrets/tests/keychain_live.rs` checks the real keychain on Linux. Its tests are `#[ignore]`d: an ordinary `cargo test` never writes to a keychain. Each item they write has a scope of its own (a hash of a scratch path) and is removed again. The default image has no Secret Service, which is what the second test wants; the first needs a derived image with GNOME Keyring and `secret-tool` (not added to the default image):

```sh
mkdir -p /tmp/pi-keyring-img /tmp/pi-live && cd /tmp/pi-keyring-img
printf 'FROM pi-desktop-xvfb:latest\nRUN apt-get update && apt-get install -y --no-install-recommends gnome-keyring libsecret-tools && rm -rf /var/lib/apt/lists/*\n' > Dockerfile
docker build -t pi-desktop-keyring:latest .
cd <repo>/desktop && cargo test -p pistudiodesktop-secrets --test keychain_live --no-run   # prints the binary's path
cp <that binary> /tmp/pi-live/keychain_live
cat > /tmp/pi-live/with-keyring.sh <<'EOF'
set -e
eval "$(printf 'test-password' | gnome-keyring-daemon --unlock --components=secrets 2>/dev/null)"   # creates and unlocks the login keyring
sleep 1
eval "$(gnome-keyring-daemon --start --components=secrets 2>/dev/null)"   # serves it on the session bus
sleep 1
/tmp/pi-live/keychain_live --ignored --test-threads=1 set_get_and_delete --nocapture
EOF
# with a Secret Service: set, get, delete, and `secret-tool lookup service com.avatsaev.pi-studio username <scope>/<entry id>/<kind>` sees the item
docker run --rm -v /tmp/pi-live:/tmp/pi-live:ro pi-desktop-keyring dbus-run-session -- bash /tmp/pi-live/with-keyring.sh
# without one (default image; with a bus that nobody answers on, and with no bus): the probe says `unavailable` within 2 s
docker run --rm -v /tmp/pi-live:/tmp/pi-live:ro pi-desktop-xvfb dbus-run-session -- /tmp/pi-live/keychain_live --ignored --nocapture the_probe_without
docker run --rm -v /tmp/pi-live:/tmp/pi-live:ro pi-desktop-xvfb /tmp/pi-live/keychain_live --ignored --nocapture the_probe_without
```

Order matters in the keyring script: with the daemon started first, or `--unlock` alone, the `login` collection is missing or locked and every write fails (`denied`) or waits for a prompt that has no display. In the derived image a bus activates GNOME Keyring on its own, so its probe succeeds even without the script: the probe reads an item and cannot tell a locked or missing `login` collection (a later `set` then fails with `denied`).

**The secret store in the real webview** (checked on Linux 2026-11-21, sprint-113/task-008). Copy the built binary to a private directory, give the container the host's network and your user (`--user $(id -u):$(id -g)`, so that the scratch files stay yours), mount a scratch directory as `/scratch` and run, inside it, a D-Bus session bus (§ above), for the keychain case the unlock-then-start sequence of `with-keyring.sh`, an explicit `Xvfb :99 &` (under `--user`, `xvfb-run` never starts its command) and `TAURI_WEBVIEW_AUTOMATION=true WebKitWebDriver --port=<free> --host=127.0.0.1`. A Node script on the host then drives it with `scripts/platform-checks/webdriver.mjs` (`Session.open(base, webkitCapabilities({application, args: ["--config-dir", "/scratch/cfg"]}))`; the app takes no `--secret-store` when the choice itself is under test) and `page-ui.mjs`. `session.invoke("boot")` shows `secretStore`; `session.invoke("engine_command", {id: "daemon.add", params})` is what the page calls for the daemon commands; the keychain is read with `docker exec -e DBUS_SESSION_BUS_ADDRESS=$(cat /scratch/bus) <container> secret-tool search --all service com.avatsaev.pi-studio`. A direct entry that connects needs a daemon on the host with `PI_STUDIO_PASSWORD` (`PI_STUDIO_HOME` scratch, `PI_STUDIO_LISTEN=127.0.0.1:<port>`); a relay entry needs `node packages/relay/dist/relay-main.js` (`PI_STUDIO_RELAY_LISTEN`), the daemon with `PI_STUDIO_RELAY_ENABLED=true`, `PI_STUDIO_RELAY_ENDPOINT=127.0.0.1:<port>`, `PI_STUDIO_RELAY_USE_TLS=false`, and the link from `PI_STUDIO_HOME=… node packages/cli/dist/cli.js --json daemon pair` (same relay variables). Use ports from the OS (never 6767) and remove the containers and processes after.

**The resume signals in the real webview** (checked on Linux 2026-11-21, sprint-114/task-004; the socket was still the webview's; re-run with the proxied connection on 2026-11-22: § The resume signals through the proxy). Same container as above, with three changes: no `--network host` (the dummy interface must not touch the host), `--cap-add NET_ADMIN`, and the daemon on the host listening on the Docker bridge's address (`172.17.0.1:<free port>`, `PI_STUDIO_HOME` scratch, `node packages/server/dist/daemon/dev-main.js`, the mock agent); the WebDriver port is published (`-p 127.0.0.1:<wd>:<wd>`, `WebKitWebDriver --host=0.0.0.0`) and the app gets `--control 7979 --control-token-file /scratch/control.token` so that `ui.inspect` shows `connection.resumeSignals`. The page is pointed at the daemon with `engine_command daemon.add {kind:"direct", name, address}` and the switcher (`chooseInSwitcher`). The image has no `ip`: mount the host's `ip` and its libraries (`ldd $(which ip)`, same Ubuntu) and run it as `docker exec -u 0 <c> env LD_LIBRARY_PATH=/ipl /ipl/ip …` (the container itself runs as your user).

`apps/ipc-bench` is the measuring instrument of the transport bridge's gate (`swe/features/desktop-transport-bridge.md` § 1). A small Tauri app: its page (`page/`, plain ES modules, no npm package and no entry in the root `package-lock.json`) runs the workloads against a WebSocket server in the same process, on `127.0.0.1` and a free port, and Rust writes `results.json` and exits. It is a workspace member, exempt from the layer rules, with its own `tauri.conf.json`, capability and sixteen commands (`bench_config`, `bench_rss`, `bench_progress`, `bench_finish`, `bench_window_hold`, `bench_tick_start`, `bench_tick_stop`, the seven `bridge_*` ones below and `proxy_open`, `proxy_stats`); it holds the channel candidates' frame codec, inbound window and outbound order buffer itself (`src/codec.rs`, `window.rs`, `order.rs`, `limits.rs`: they moved here from the `net` crate, P16, because the shipped bridge is the loopback proxy and has none of them), depends on the `net` crate only for its 128 MiB message limit, and on `getrandom` (the proxy's token); it is never bundled or released and the shipped app has nothing of it. Rows B1 to B5 (B2 with 4 KiB, 64 KiB and 256 KiB frames) run over four transports in `page/transport.js`: the page's own `WebSocket` (the baseline), two candidate bridges, `bridge-frame` and `bridge-batch`, and `proxy-ws`, a loopback WebSocket proxy owned by Rust (below). B6 (order and integrity) is checked in every workload of every transport. W1 (`--only window`) is the candidates' no-acknowledgement test: for the bridges the page never acknowledges a 128 MiB flood, Rust must stop reading just past the 8 MiB window (the bytes it holds stop there and the server's sends stall), then the page acknowledges and the flood must arrive whole; for `proxy-ws`, which has nothing to acknowledge, the page reads nothing for 3 s (its main thread is kept busy in the first frame's handler), Rust must hold only a few frames (at most 512 KiB), the flood must arrive whole, and the record says whether the server's sends stalled (`stalls`, `stalledAtServerFedBytes`) and how far the app's memory grew. B7 and B8 (`page/load.js`, below) run on all four transports.

**The candidates** (`src/bridge.rs`, `src/bridge_commands.rs`, `page/bridge.js`, `page/batch.js`): Rust holds a client socket to the benchmark's own server and forwards between it and the page. Inbound goes over a Tauri `Channel`: `bridge-frame` sends one channel message per WebSocket message (raw for binary, JSON for text), `bridge-batch` sends batches in the codec's format (`src/codec.rs`), flushed when 64 KiB is waiting or the socket has nothing more to read right now. Outbound goes through commands shaped like the spec's: `bridge_open` (`url`, `inbound`, a `Channel`), `bridge_send_text` (`handle`, `seq`, `data`), `bridge_send_binary` (a raw body with the headers `handle` and `seq`), `bridge_ack`, `bridge_close`, plus `bridge_send_batch` (a raw body in the codec's format under one `seq`) and `bridge_stats` (the counters of a connection). `bridge-frame` sends one invoke per frame; `bridge-batch` sends the frames queued in the same task as one raw invoke. In both, the `InboundWindow` (`src/window.rs`) counts the payload bytes sent and the page acknowledges every 256 KiB or 50 ms (stop reading above 8 MiB, resume below 4 MiB), and the `OrderBuffer` puts sends back in `seq` order before the write task writes them; the write task flushes once per queued group and answers each send after the flush. The page's `bufferedAmount` adds a frame's bytes at send and subtracts them at the send's answer. The socket is plain and local: no TLS, password or error classes, and the order buffer's 5 s gap timer and the 16 MiB byte cap of the spec are not part of the benchmark (a gap shows as a run that times out).

**A connection that ends while the page is behind.** Rust reads the socket faster than the page can take what it sends (up to the two bounds below), so the socket can end (the server's flood is over, or the server dropped it) while the page is still working through the channel. Rust then forgets the handle and sends `closed` last on the channel; an acknowledgement the page had in flight answers `unknown_handle`. The page ignores that answer (the `closed` message says what happened), reports a refused send (after waiting up to 250 ms for `closed`, so the error it reports is the cause), and `bridge_stats` still answers with the counters the connection had when it ended, with `ended` (by the page or by itself, the code, the reason, the error). A connection that ends by itself is logged on the standard error stream (`bridge connection ended by itself: code, reason, error`, with the frames, bytes and messages sent and unacknowledged), and the server waits up to 60 s for the page to close a finished stream before it drops it.

**The two bounds, and the watchdog.** Rust stops reading the socket while more than 8 MiB (`src/window.rs`) *or* more than `--max-inflight-messages` (default 512) channel messages are unacknowledged, and resumes below half of each; acknowledgements carry bytes and messages (`bridge_ack` `handle`, `bytes`, `messages`) and the page sends one at a quarter of the message bound (the `bridge_open` answer names it as `maxMessages`), at 256 KiB, or 50 ms after the first thing it owes. A *message* is one channel message (one `eval` or one fetch in the webview); a batch is one. The byte window alone does not bound the webview's queue: on Windows (WebView2) Tauri hands a small channel message to the page as a script to evaluate, and about 12,000 queued 32-byte frames made `Channel::send` fail (`channel_failed`) in the full runner run, which ended the connection; the `closed` message that should say so cannot be delivered over the channel that failed, so the page learned nothing and waited out its timeout. Two consequences for the real bridge: Rust counts messages next to bytes, and the page cannot rely on `closed`. A run that sees no frame and no end for 30 s (`page/run.js`, `STALL_MS`; a running harness command or a changing `bufferedAmount` counts as life) fails at once with the transport's counters (`describe()`: frames and bytes sent, unacknowledged messages and bytes, the peaks against the bounds, whether and why the connection ended), instead of waiting out the 10-minute run timeout; the runs and rows after it still run, and the exit code is 1. The peak is in each record as `ipc.maxMessagesInFlight` (next to `maxOutstanding`), and `results.bridge.window` holds the two bounds (`maxBytes`, `maxMessages`).

**A lost channel message (`page/watch.js`).** On the macOS runner (run 3) `bridge-frame` B2/4 KiB run 1 stalled: Rust had sent 24,425 messages, the page had delivered and acknowledged 23,912, and Rust's 513 unacknowledged messages were exactly the ones the page never got, so Rust stopped reading (more than 512) while the page waited for frames: one message of Tauri's channel was lost on its way to the page and the 512 after it were held behind it. Tauri's JS `Channel` delivers in index order and holds later messages behind a missing index for ever (`@tauri-apps/api` `core.js` `Channel`, `scripts/core.js`); a raw message of 1,024 bytes or more goes through the fetch path (`tauri-2.12.5/src/ipc/channel.rs:302-321`: parked in `ChannelDataIpcQueue`, then an evaluated script `invoke('plugin:__TAURI_CHANNEL__|fetch')…then(runCallback).catch(console.error)`), where a fetch that fails or never settles loses its index; `Channel::send` returns `Ok` once the script is queued (`channel.rs:297-320`), so Rust is told nothing, and the cache has no size or count limit (513 in flight cannot overflow or evict it). Of the three suspects only that fits the counts: the acknowledgements all arrived (Rust's acknowledged count, 24,425 − 513, equals the page's delivered count, so none was lost or refused: a refused one fails the run), the page's 50 ms timer runs whether or not frames arrive, a throwing `onmessage` does not stop the pump (the global bundle's `Channel` catches it: `queueMicrotask`), and the page has no delivery queue of its own. The cause of the loss itself is not proven: a candidate on macOS is `wry-0.57.2` `src/wkwebview/class/url_scheme_handler.rs:163-203, 336-343`, which silently drops the response of a custom-protocol task whose key was removed (`stopURLSchemeTask:`) or reused, so the page's fetch never settles and Tauri's JS `.catch(console.error)` never runs. The page now says which it is when a run stalls: `describe()` adds the raw callbacks Tauri's channel got before it reorders them (the page wraps the callback in `__TAURI_INTERNALS__.callbacks`), the next index it waits for, the highest seen, the gap (`missingIndexes`) and how many wait behind it, the fetches of channel data by outcome (started, ok, answered with an error, rejected, still pending), the last console errors, and Rust's `channelSendErrors` (`Channel::send` calls that failed; the fetch's outcome is not observable from Rust: `ChannelDataIpcQueue` has no public accessor), then a `DIAGNOSIS` (a lost message, a lost tail, acknowledgements that never reached Rust). The same record is in every run's `ipc.page` (`channel`, `fetches`, `console`). On Linux (WebKitGTK, a different custom-protocol path) the stall did not reproduce: 35 B2 runs of `bridge-frame` at 4 KiB (20 in one process, 15 each in a fresh process after B1, about 65,000 fetched messages per run) had none.

**The proxy transport, `proxy-ws`** (`src/proxy.rs`, `src/proxy_commands.rs`, `createProxyTransport` in `page/transport.js`): the fourth candidate, for when the Tauri channel is the bottleneck. Rust still owns the real socket to the server (where the shipped app would hold TLS and certificates, later an SSH or relay leg), but the bytes reach the page over the webview's own `WebSocket` to `ws://127.0.0.1:<port>/<token>`, so the page side is the baseline's code and B5's `bufferedAmount`, B6 and the rest read unchanged. `proxy_open(url)` dials the server (a failure is the command's error), binds `127.0.0.1:0`, mints a 256-bit token (`getrandom`) and answers `{ url, id }`; `proxy_stats(id)` answers the counters of the connection, kept after it ends. **One listener per connection**, not one per app: the port exists only until the page's upgrade is accepted or 10 s have passed, so no port stays open between connections, a token has nothing to select that the port does not, and the cost is one bind (microseconds). The upgrade is accepted only if its path is the token (constant-time compare, used once by the first request that passes; a wrong guess does not use it up) and its `Origin` is the page's own, read from the calling webview's address (expected `tauri://localhost` on Linux and macOS and `http://tauri.localhost` on Windows; `results.app.pageOrigin` and `ipc.pageOrigin` record what the page's `location.origin` actually is, and a refused upgrade's error says what Rust expected and refused, without the token); anything else gets a bare 403. Then one task per direction pumps frames as they are (text and binary, pings and pongs), coalescing what has already arrived into one write (at most 256 KiB or 64 frames), a close frame (code and reason) is forwarded to the other side and its answer waited for, and a side that ends without one (a reset) ends the other by dropping its socket, so the page sees 1006. Backpressure is the await: a direction reads again only when its write is done, so a socket that stops taking data stalls the other end through TCP and Rust holds a write batch and a frame (the Rust tests: a client that never reads stalls a 96 MiB flood with at most 256 KiB and a frame held). Whether a webview's socket ever stops taking data is the webview's business: in W1 on Linux (WebKitGTK, Xvfb) a page that read nothing for 3 s still had all 128 MiB taken (no write stalled; the app's memory grew by up to 138 MiB), so the bound that holds is Rust's, not the page's. The record per connection (`ipc`): frames and bytes each way, `maxOutstanding` (the most Rust held between the sockets), `stalls` (writes to the page over 250 ms), `maxWriteMs`, `stalledAtServerFedBytes` (what the server had sent when the first write stalled), `refusals`, `ended` (who closed, whether with a handshake, code, reason). One honest limit of the pump: the answer to a close is the library's echo of the code, not the other side's own answer. The server's `/close?code=C` path (3000 to 4999) exists to test close codes from the server's side. This is the measured sketch of the shipped proxy, `crates/net/src/proxy/` (the `net` crate: TLS and the password on the daemon's leg, the `Host` check, the 128 MiB cap, the 2 s close wait, a set of at most four connections), which was built from it and is tested without Tauri; the sketch stays as it was measured. The bench app's CSP (`tauri.conf.json`) allows the page's WebSocket to `ws://127.0.0.1:*`; the shipped app's (`apps/pistudiodesktop/src-tauri/tauri.conf.json`) says `connect-src 'self' ipc: http://ipc.localhost ws: wss: blob:`, which already allows it (and any other `ws:` host: the proxy would need no CSP change).

The server picks its behaviour by path: `/echo`; `/flood?frames=N&size=S&kind=binary|text` (waits for the text `go`, then sends N frames and a closing JSON message with the count and the running hash); `/mixed?frames=N&size=S` (a binary `/flood` that also echoes, between two frames, every message the page has sent, and keeps echoing after the closing message until the page closes: B7); `/paced?rate=R&seconds=T&size=S` (after `go`, `R` binary frames a second for `T` seconds in 10 ms ticks, a late tick making up what is due, then the flood's closing message: B8); `/sink` (checks what it receives, answers a report on the text `end`). Every frame carries its counter and a checksum, every stream a running hash (`src/frame.rs`, mirrored in `page/frame.js`; the same vectors are tested in both).

```sh
cargo build --release -p pistudiodesktop-ipc-bench      # measure only with a release build
cargo run --release -p pistudiodesktop-ipc-bench -- --out /tmp/results.json --scale 0.1
node --test 'apps/ipc-bench/page/*.test.mjs'            # the page's half: frame format, batch codec, bridge transport, comparison
```

| Option | Effect |
|---|---|
| `--out FILE` | Where `results.json` goes (default `results.json` in the current directory) |
| `--runs N` | Runs of each workload (default 3) |
| `--only ROWS` | A comma-separated subset of `b1,b2,b3,b4,b5,window,b7,b8` (`window` is the candidates' no-acknowledgement test; the baseline skips it) |
| `--scale F` | Shrink every count and byte total to the fraction `F` (above 0, at most 1): `0.1` is a quick run |
| `--corrupt N` | The server changes a byte of frame N of each stream it sends (and of what it receives): the run must exit 1 and name the workload and the frame |
| `--swap N` | The server sends frame N after frame N+1 (on `/sink` it checks the frame it received as N after N+1); `/echo` answers one frame at a time and cannot |
| `--timeout S` | Give up with exit 1 after S seconds (default 3600) |
| `--max-inflight-messages N` | The candidates stop reading the socket while more than N channel messages are unacknowledged (default 512, 1 to 1,000,000); also bounded by 8 MiB. Recorded as `results.bridge.window.maxMessages` |

The app runs unattended and exits 0 when every run completed and B6 found nothing, 1 otherwise; the problems are printed as `PROBLEM <transport> <workload> run <n>: frame <k>: …`. The reading of the baseline against the candidates is printed at the end as `PASS`/`FAIL` lines. In the `pi-desktop-xvfb` container (see § Without a display; mount a writable directory for the results):

```sh
mkdir -p /tmp/ipc-bench && cat > /tmp/ipc-bench/run.sh <<'EOF'
cd /work
xvfb-run -a ./target/release/ipc-bench --out /out/results.json "$@"
EOF
docker run --rm -v "$PWD:/work:ro" -v /tmp/ipc-bench:/out pi-desktop-xvfb bash /out/run.sh --scale 0.1
```

`results.json` (`schema` 2) holds the platform, the webview's user agent, the Tauri version, the options, the timer's step and, per transport, every run's raw measurements (durations, bytes, frames, percentiles, the memory samples of B4, the integrity result, and for a candidate the `ipc` record of the run) and a `summary` with the worst and the median run of each metric. For a candidate, `ipc` (per transport: `ipc`) says which way raw bodies reached Rust (`custom protocol (raw bytes)`, or `postMessage (JSON array)` when Tauri fell back after one failed fetch), how many sends arrived out of `seq` order (and the most frames that waited for an earlier one), how many channel messages Tauri evaluated into the page and how many the page fetched (a raw message under 1,024 bytes and a JSON one under 8,192 are evaluated), the most bytes unacknowledged, and the window's numbers. `comparison` is a first reading of each candidate against the baseline with the pass column of the spec's § 1 (a `pass: false` row is a finding, not a failed run: only an incomplete run or a damaged frame makes the exit code 1). Four things to read it with:

- The page's timer (`performance.now()`) steps by 1 ms in WebKit: a round trip under 1 ms reads 0 or 1. B1's `medianMs` and `p99Ms` are quantized by it; `meanMs` (the total over the trips) is not. `timerResolutionMs` says what the page saw.
- Every check (counter, checksum, running hash) costs the page the same in every transport: `pageHash.mibPerS` says how fast the page hashes.
- B4's memory is the sum of the resident memory of the app and its descendants (`/proc` on Linux, `ps` on macOS, PowerShell on Windows), sampled every 250 ms (at least once a second) from before the run to after it: `memory.samples` holds every sample, `growthKiB` is the peak minus the start. On macOS the web content process is not a child of the app, so read `processesAtStart` before trusting the total. Only Linux has been run. The reading of a run (`page/compare.js`) passes a candidate's growth when it is at most the baseline's growth in the same run plus 64 MiB (P14), and fails it when the run has no baseline growth to compare with.
- B5's `bufferedAmountEnd` is read once the answers of the last sends have arrived (waiting at most 2 s; `settleMs` says how long it took): through a bridge the sink's report can overtake them. `bufferedAmountAtReport` is the number at the report itself.

**B7 and B8** (`page/load.js`, `page/hidden.js`, `page/worker-timers.js`, `src/tick.rs`, `bench_window_hold` in `src/commands.rs`).

- **B7** runs B1's echo (32-byte frames, one at a time, 5 warm-up trips not counted) on the same connection while B4's download (1 GiB as 32 KiB frames, `/mixed`) runs, until the download's closing message. The record has the trips, the mean, median, 90th and 99th percentile, the maximum and the 20 slowest round trips, and the download's own rate; both streams are checked (B6). It is reported only: one socket is shared, as in the app today. WebKit's timer steps by 1 ms, so the 99th percentile is quantised; the baseline finishes the download in a second or so, so its trip count is small (`trips`).
- **B8** runs `/paced` at 1,000 frames a second of 4 KiB for the hidden period plus 2 s (30 s hidden at full scale, 2 s at least when scaled), twice per transport: `B8/hide` (`window.hide()` then `show()`) and `B8/minimise` (`minimize()` then `unminimize()`). Rust does the whole hold (`bench_window_hold`): a hidden page may run late or not at all, so it cannot be the one that shows the window again. The record has `lostFrames` (the stream's own count less the page's; B6 names each missing frame), `heldBytes` (Rust's most unacknowledged bytes, `null` for the baseline: the webview's own buffers cannot be read) against the window (8 MiB and a frame: more is a problem and fails the run), `framesDeliveredWhileHidden` and `framesBehindAtShow` (the page's deliveries against the stream's clock), `catchUpMs` (from the show until the page is within 100 frames of the stream), `window` (what the system said after each request, and the `visibilitychange` events the page saw: `systemHidIt`, `pageSawHidden`), `workerTimer`, `pageTimer` and `rustTick`. The two timers are chains of 500 ms timers, each armed when the last fired (as the app's reconnect timers are): the worker one is the source of `packages/workbench/src/host/browser-worker-timers.ts` (a test fails when `page/worker-timers.js` drifts from it), the page one is `setTimeout`; each reports `expectedFires` and `firedWhileHidden` (a stopped timer fires nothing) and `maxDelayMs`, the lateness of the fires that were due while the window was away (also when they fired after it came back, and for the timer still waiting at the end). `rustTick` is a 2 s tick on the Rust side (`src/tick.rs`) over the whole run: `maxGapMs` is its longest sleep and `maxDelayMs` how much later than 2 s that was; the wake detector of the app's connection resilience uses such a tick. The timers and the tick decide nothing here: the note reports them and the owner decides P7.
- Under Xvfb a hidden window is not a real desktop's: with no window manager `minimize()` is accepted and does nothing (`window.afterHide.minimized` stays false, `pageSawHidden` false), and WebKitGTK keeps running a hidden page's timers and deliveries, so the page never falls behind and the window bound is not stressed (W1 is the test of the bound). The runners and a real machine are the evidence for P7. To minimise under a window manager in the container, derive an image (`FROM pi-desktop-xvfb:latest`, `RUN apt-get update && apt-get install -y --no-install-recommends openbox`) and start it before the benchmark: `xvfb-run -a bash -c 'openbox & sleep 1; exec ./target/release/ipc-bench "$@"' _ --out /out/results.json`.

**On the macOS and Windows runners** (`.github/workflows/desktop-ipc-benchmark.yml`): builds `ipc-bench` in release mode on `macos-15` and `windows-latest` and runs it with `--runs` and `--scale` (no npm install, no WebDriver, no machine policy). It runs only when started by hand, from Actions → Desktop IPC benchmark → Run workflow (inputs `runs`, default 3, and `scale`, default 1; `runs=1`, `scale=0.1` is a quick run; the full run takes about 20 to 30 minutes). Until 2026-11-22 a pull request that changed the workflow file or `apps/ipc-bench` also started it; that trigger was removed once the benchmark had decided the transport (decision T5). It never runs on a push to `main`, and `release.yml` ignores `desktop/**` and `.github/workflows/desktop-*.yml`. Results: the job summary (runner CPU model, core count, OS, webview version, the user agent, a table of the summary rows and the PASS/FAIL comparison) and an artifact per platform, `ipc-benchmark-macos` and `ipc-benchmark-windows`, with `results.json` and `bench.log`. ## Platform checks on macOS and Windows runners

`apps/pistudiodesktop/scripts/platform-checks.mjs` (helpers in `scripts/platform-checks/`, run by `.github/workflows/desktop-platform-checks.yml`) checks on a runner what a machine can check; `docs/platform-checks.md` says which items it covers. Modes: `macos` (the control socket only), `windows` (WebDriver through `tauri-driver` and `msedgedriver`) and `rehearse-webdriver`, which runs the Windows checks on Linux against a `WebKitWebDriver` already listening (the container of § Without a display), so the script can be tried without a Windows machine. It writes `summary.md` and `results.json`, appends the summary to `GITHUB_STEP_SUMMARY` and exits 1 when a check fails. Its unit tests run with the app's `npm test`.

**Milestone 2's checks** (sprint-117/task-002). Pure readers and tests: `bridge.mjs` (`connection` from `ui.inspect`: one open transport with frames in, the wake wait `stopAndContinue`, the keychain scope and account names, the parsers of `security find-generic-password` and `cmdkey /list`), `stand-in-daemon.mjs` (the Windows job's daemon: `node:http` and its own WebSocket framing, no dependency, because that job installs only the desktop frontend's packages; it answers a `hello` with the `frame` of `packages/protocol/fixtures/external-clients/status.server_info.json` and a `ping` with a `pong`, reads the bearer password from the subprotocol and echoes it), `suspend.mjs` (macOS: `SIGSTOP` and `SIGCONT` of the app's process; Windows: a PowerShell script, passed with `-EncodedCommand`, that calls `NtSuspendProcess` and `NtResumeProcess` on the app and all its descendants, the webview's processes among them). The checks: `macos.mjs` (`bridge.macos.transport-open` and `bridge.macos.wake`, after the local daemon starts), `macos-keychain.mjs` (`keychain.macos.item`) and `windows-bridge.mjs` (`bridge.windows.*`, `keychain.windows.credential`). A keychain check that cannot run on a runner (the app exits with `--secret-store keychain`, a control call waits for a prompt for 30 s, or the store refuses) is skipped with that reason and a fact in the summary says whether the runner can use its keychain unattended; each such check deletes its items in a `finally`.

**Rehearsing the Windows page checks on Linux** (done 2026-11-22: 12 passed, 3 skipped): copy the debug binary to a private directory, run `docker run -d --name rehearse --network host --user "$(id -u):$(id -g)" -v /tmp:/tmp -e HOME=<dir> pi-desktop-xvfb bash -c 'Xvfb :99 -screen 0 1280x800x24 & export DISPLAY=:99; sleep 1; dbus-daemon --session --fork --print-address=3 3>/tmp/bus; export DBUS_SESSION_BUS_ADDRESS=$(cat /tmp/bus); TAURI_WEBVIEW_AUTOMATION=true exec WebKitWebDriver --port=<free> --host=127.0.0.1'`, then, on the host, `node scripts/platform-checks.mjs rehearse-webdriver --app <that binary> --webdriver-url http://127.0.0.1:<free> --out <dir>`. **The update check** (`scripts/platform-checks/update-check.mjs`, sprint-134/task-001; the release workflow runs it per system after a release). It installs a build, launches it with `--control <free port> --control-token-file --secret-store=file --config-dir <scratch> --update-manifest <url>`, and drives `update.check` (waits for `available`), `update.install` (waits for `restart_needed`), `update.restart` (the old process must exit; the restarted app is found again on the same port and token) through `scripts/platform-checks/control-client.mjs`, then proves the result from `ui.inspect.update` (`current` is the expected version, `manifest` is `override`, no `lastError`, state not `failed`), a new process (`pgrep -f` / PowerShell on the token file's path) and the installed file replaced (inode, mtime or ctime changed; its SHA-256 is printed). `--from <installer> --manifest <latest.json> --expect-version <N> [--self-check-manifest <self-check.json>]` is P to N (and then N to N on the same install); `--self-check --from <N's installer> --manifest <self-check.json>` is N to N alone. The kind comes from the installer's name (`.AppImage`, `.deb`, `.dmg`, `-setup.exe`). Install per system: AppImage copy and `chmod`; `.deb` `sudo -n apt-get install -y <file>` plus a polkit rule for the runner's user (`/etc/polkit-1/rules.d/49-pi-studio-update-check.rules`, removed at the end) so the app's `pkexec` needs no agent; macOS `hdiutil attach`, `ditto` into `/Applications`, `xattr -dr com.apple.quarantine`, `hdiutil detach`; Windows the NSIS `/S` (per user). Every step has a time limit (install and download 300 s by default, `--install-timeout`), so a dialog nobody answers fails the step. Linux needs a display and a session bus: run it as `dbus-run-session -- xvfb-run -a node …`; where there is no FUSE set `APPIMAGE_EXTRACT_AND_RUN=1`. The unit tests (`update-check.test.mjs`) cover the arguments, the expectations, the install steps per system, the polkit rule and the report. **Run on Linux in a container on 2026-11-23** (test builds 0.3.0 and 0.3.1 from a local HTTP server, a throwaway key; image `FROM pi-desktop-xvfb` plus `sudo polkitd pkexec dbus`, a non-root user with passwordless sudo, system D-Bus and `polkitd` started by hand, Xvfb): AppImage 12 steps and `.deb` 13 steps passed, 8 to 9 s each; `pkexec` without the rule fails with exit 127 (no agent), with it the install passes. The signature of a self-check file must name the self-check version (`tauri signer sign --app-version <N's next patch>-selfcheck`): the plug-in compares the signed version with the announced one.

## Debugging the frontend

In a debug build, right-click in the window and choose "Inspect Element" for the webview's
developer tools. Release builds have them off.
